## Наблюдения

1. **Двойные сообщения (API 10.50).** Каждое событие приходит дважды: в формате ProtoBuf
   (`managedAccountsProtoBuf`, `nextValidIdProtoBuf`, `errorProtoBuf`) и в классическом
   (`managedAccounts`, `nextValidId`, `error`). Адаптер должен обрабатывать **один** вариант, иначе события
   задвоятся. Решение: классические callback-и в V1; ProtoBuf-варианты только журналируются.
2. **Порядок в журнале задаёт `seq`, а не порядок строк**: тяжёлое сообщение (ProtoBuf ошибки 2104)
   записалось после более поздних. Разбор фикстур сортирует по `seq`.
3. **Код 2104** («Market data farm connection is OK») приходит при каждом подключении — информационный, не ошибка.
4. **Номер счёта Free Trial** имеет вид `DU` + буква + цифры; защита от номеров счетов в репозитории расширена под этот формат.
5. **Автоперезапуск IB Gateway** (Lock and Exit → Auto restart, 09:25 по Израилю): 7 октября 2026 после
   перезапуска Gateway сам вошёл в Free Trial без ручного входа; `connect` в 09:25:35 прошёл успешно.
   Поведение реального счёта (еженедельный повторный вход с 2FA) проверить после пополнения.
6. **Лицензия.** C#-клиент IBKR распространяется под GPL v3: для личного использования ограничений нет;
   распространение собранных программ потребовало бы соблюдения GPL. В репозиторий исходники IBKR не копируются.

_7 октября 2026, 12:04–12:13 UTC (08:04–08:13 Нью-Йорк, премаркет), Free Trial, Read-Only API, только чтение._

7. **Переподключение (P1.B.03).** Разрыв обнаруживается по `connectionClosed` / `IsConnected() = false`;
   повторное подключение — новый `EClientSocket` + `EReader`, тот же `EWrapper`, пауза 1-2-4…60 с.
   После переподключения `nextValidId` снова 1 (заявок не было), `managedAccounts` приходит заново — проверка
   `DU` повторяется. Коды 2104/2107/2158 приходят при **каждом** подключении (информационные); 2106 — только
   когда реально запрошены исторические данные. Доказательство: `reconnect`, `messages-20261007T120422Z`.
   **Через автоперезапуск (8 окт., `messages-20261008T013603Z`):** 1100 (Gateway ↔ серверы IBKR потеряны) приходит
   повторно каждые ~0,5–40 с, пока связи нет; 1102 «restored — data maintained» — без разрыва API-сокета, подписки
   живы (ядро всё равно сверяет заявки). Автоперезапуск в 09:25 закрывает сокет (`SocketException` «forcibly closed»),
   Gateway ~10 с не принимает подключения («actively refused»), затем принимает; сессия Gateway сохраняет вход —
   2FA не нужна. **Вывод для платформы:** держать переподключение с паузой до 60 с, не слать заявки около 09:25,
   после каждого переподключения — сверка (`reqOpenOrders`, `reqExecutions`), не повторная отправка.
8. **Тот же clientId дважды** → Gateway отвечает **326** («client id is already in use») и закрывает сокет
   (`SocketException 10054`). Значит, после реального разрыва повторное подключение может получить 326, пока
   Gateway не освободит старое соединение — повтор с паузой это покрывает; второй процесс с тем же clientId
   сразу получает отказ (`connect` при работающем `reconnect`, `messages-20261007T120717Z`).
9. **Счёт (P1.B.04, ✅ сверено владельцем с веб-интерфейсом 9 окт., `messages-20261008T222455Z`).** Free Trial: `AccountType` INDIVIDUAL, `NetLiquidation` = `TotalCashValue` =
   `AvailableFunds` = 1 000 000 USD (виртуальные), `BuyingPower` = 4 000 000 → **маржинальный** счёт, не Cash;
   позиций нет; валюты: USD (+ строка BASE). Из 29 тегов `AccountSummaryTags` **не пришли**: `SettledCash`,
   `PreviousDayEquityWithLoanValue`, `ReqTEquity`, `ReqTMargin` (в классе API опечатка — в `reqAccountUpdates`
   они называются `RegTEquity`/`RegTMargin`), `HighestSeverity`, `DayTradesRemaining`, `Leverage`. Расчётные деньги
   доступны через `reqAccountUpdates` как `SettledCashByDate` (`20261007:1000000`); отдельного «нерасчётного» ключа
   нет. Для основного Cash-счёта набор тегов перепроверить. Сверка с веб-интерфейсом paper-счёта — за владельцем.
   Доказательство: `account`, `messages-20261007T120731Z`.
10. **Contract details (P1.B.05).** Запрос `STK/SMART/USD` без `primaryExch` даёт ровно один контракт для всех 29;
    `stockType` ETF, часовой пояс US/Eastern, торговые часы 04:00–20:00, ликвидные 09:30–16:00 (Нью-Йорк);
    `suggestedSizeIncrement` = 40 (SPY, QQQ, IWM, GLD) или 100 — это подсказка размера для интерфейса, не ограничение
    (`sizeIncrement` = 0,0001). `contracts.csv`: тикер, `conId`, ISIN, биржи, шаг цены, размеры, типы заявок, часы.
11. **Котировки (P1.B.06)** — без купленных подписок:

    | `reqMarketDataType` | Пришло | Ошибки | Задержка |
    |---|---|---|---|
    | 1 live | ничего | 354 «not subscribed… Delayed market data is available» | — |
    | 2 frozen | ничего | 354 | — |
    | 3 delayed | `marketDataType`=3, `delayedBid/Ask/Last/Close/Open` | 10167 (предупреждение) | последняя сделка SPY ровно 15,0 мин назад; первый тик через 0,9–1,5 с |
    | 4 delayed-frozen | то же, `marketDataType`=3 (сессия открыта, «заморозки» нет) | 10167 | 15 мин |

    Бесплатный снимок (`snapshot=true`, не регуляторный) для типов 3/4 заканчивается `tickSnapshotEnd` через 3–4 с;
    `tickReqParams.snapshotPermissions` = 0. Отмена отклонённого запроса даёт 300 «Can't find EId» — безвредно.
    Первый замер — в премаркет: спреды (VWO 59,58/60,02) не годятся для калибровки `half_spread_bps`.
    **Повтор в часы торгов** (7 окт., 13:59 ET, `out/quotes-20261007T175927Z.csv`, `messages-20261007T175932Z`):
    то же — типы 1/2 → 354 / **10168** («Delayed market data is not enabled» для снимка и типа 2), данных нет;
    типы 3/4 → задержанные, возраст последней сделки 15,0–15,5 мин, первый тик через 0,4–1,4 с, снимок за 0,8–1,4 с.
    Задержанный спред в часы торгов узкий: SPY 777,43/777,44, VWO 59,88/59,89 (1 цент).
    **После закрытия** (7 окт., 21:34 ET = 8 окт. 04:34 по Израилю, `messages-20261008T013442Z`): типы 1/2 → 354, данных нет; тип 4 по-прежнему приходит как
    `marketDataType` = 3, а не 4: SPY торговался в расширенной сессии до 19:59 ET, поэтому «заморозки» нет.
    Возраст последней сделки: SPY 96 мин, VWO 224 мин (последняя сделка VWO в 17:51 ET); спред VWO
    вне сессии широкий (59,58/59,89). **Вывод:** без подписок программа видит только задержанные на 15 мин
    котировки в сессию и устаревшие вне её. Для решений по дневным барам после закрытия этого достаточно,
    а проверка «котировка свежая» перед входом требует подписки (стоимость — после пополнения). **Стоимость** подписок не проверялась (Free Trial,
    покупок нет) — посмотреть в Client Portal основного счёта. Для стратегии на дневных барах задержанных данных
    достаточно для просмотра, но правило «задержанная котировка блокирует вход» остаётся.
