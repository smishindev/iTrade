## 0. Коротко

| | |
|---|---|
| **Что строим** | Личную локальную торговую платформу. Она находит идеи по формализованной стратегии, показывает основания, риск и издержки, после вашего подтверждения отправляет ордера в IBKR, ведёт проверяемый журнал, сверку с брокером и налоговый экспорт. |
| **Стек** | **React 19 + TypeScript** (интерфейс) · **C# / .NET 10 LTS + ASP.NET Core** (вся торговая логика) · **PostgreSQL 18** (состояние) · **Parquet** (снимки данных) · **IBKR TWS API (C#)** через **IB Gateway**. Python — только исследования и эталон для тестов, без права торговать. |
| **Где работает** | На вашем ПК. Сервер не нужен. Компьютер включается **раз в торговый день на 10–20 минут, в любое время в окне примерно 16 часов** (см. §7). |
| **Первая стратегия** | `ETF_PULLBACK_V1` — откат в восходящем тренде на ликвидных ETF, удержание до 10 сессий. |
| **Порядок** | Сначала **две быстрые проверки (~50 ч)**: есть ли у стратегии преимущество после издержек и можно ли её исполнить в IBKR на вашем счёте. Платформу (~300–450 ч) строим **только при двух «да»**. |
| **Расходы** | Инфраструктура ≈ $0 в месяц. Отдельно: комиссии IBKR, возможные подписки на котировки, разовая консультация бухгалтера. |

**Главный принцип:** сначала доказать гипотезу и осуществимость, потом строить надёжное исполнение,
и только потом рисковать небольшим капиталом. Не наоборот.

## 1. Цель и границы первой версии

**Цель V1:** собственный инструмент активной торговли, который позволяет проверять идеи,
принимать воспроизводимые решения, корректно их исполнять и измерять результат после расходов и налога.

| Область | Решение V1 |
|---|---|
| Пользователь | Только вы. Без клиентов и чужих денег (лицензия не нужна). |
| Инструменты | Обычные американские ETF: широкий рынок, сектора, страны, облигации, золото. Без плечевых, обратных, ETN. |
| Направление | Только покупка → продажа. Без коротких позиций, опционов, фьючерсов, крипты. |
| Счёт | IBKR, **cash account** (без маржи). |
| Горизонт | Дни; предел удержания — 10 торговых сессий. |
| Вход | **Только после вашего подтверждения** каждой идеи. |
| Выход | По правилам, утверждённым вместе со входом: защитный стоп у брокера + выход по сигналу. |
| Исполнение | Программа отправляет только утверждённые заявки, в утверждённых границах. Сама новых сделок не выбирает. |
| Интерфейс | Локальное веб-приложение (`https://localhost`). |
| Размещение | Ваш ПК. Без VPS и без Docker для приложения (Docker только для PostgreSQL). |
| Капитал | 10 000 ₪ ≈ **$3 280** (курс 3,05 на 06.10.2026). Реальный лимит пилота задаётся отдельно. |
| Валюты | Сделки в USD; капитал, отчёты и налог — в ILS. |

**Сознательно не делаем в V1:** десятки стратегий, торговля внутри дня, LLM-агент с правом торговать,
автоматический выбор сделок, мобильное приложение, облако, уведомления в мессенджерах, чужие счета.

| Что | Выбор |
|---|---|

### 2.5 Python: роль строго ограничена

Python остаётся, потому что он уже работает и быстрее всего для исследований:
1. **Проверка A** — быстрый бэктест гипотезы до того, как строить C#-ядро.
2. **Эталон (oracle)** — независимая реализация индикаторов и упрощённого бэктеста. C#-ядро обязано
   совпасть с ним на тестовых наборах (дифференциальные тесты ловят ошибки в обеих реализациях).
3. Загрузка бесплатной истории (Yahoo) и календаря NYSE → Parquet.
4. Статистика: доверительные интервалы, бутстрэп.

**Python никогда не подключается к IBKR и не пишет в торговые таблицы** (это закреплено в хуках Claude Code).
Финальный тест стратегии запускает то же C#-ядро, что и рабочее приложение.

## 3. Архитектура

### 3.1 Процессы

```
 Браузер ──HTTPS + SignalR──►  ITrade.Host  (ASP.NET Core, слушает только 127.0.0.1)
 (localhost)                    │  отдаёт React, API, фоновые задания, ЕДИНСТВЕННЫЙ отправитель ордеров
                                ├── EF Core ──────────► PostgreSQL 18 (Docker, 127.0.0.1:5432)
                                ├── файлы ────────────► D:\ITradeData\ (raw, datasets, exports, logs)
                                └── TCP 127.0.0.1:4002/4001 ──► IB Gateway ──► серверы IBKR ──► биржа

 ITrade.Research.Runner (CLI) ──► PostgreSQL (чтение + таблицы исследований), Parquet
                                   ✗ нет ссылки на брокерский адаптер, нет торговых секретов

 python/ (uv)  ──► Parquet-снимки (история, календарь), эталонные тесты
                   ✗ нет доступа к IBKR и к торговым таблицам
```

### 3.2 Проекты решения (.NET)

| Проект | Ответственность | Может зависеть от |
|---|---|---|
| `ITrade.Domain` | Типы: `Money`, `Quantity`, `InstrumentId`, `TradeDate`, `OrderState`, контракты стратегий и риска | ничего |
| `ITrade.Strategies` | Индикаторы и правила. **Чистые функции**: без времени, сети, БД | Domain |
| `ITrade.Simulation` | Портфельный событийный бэктест, модели исполнения, модель издержек | Domain, Strategies |
| `ITrade.Application` | Сценарии: сканирование, подтверждение, резервирование, исполнение, сверка, отчёты. Интерфейсы `IBrokerGateway`, `IMarketData`, `IClock` | Domain, Strategies, Simulation |
| `ITrade.Infrastructure` | EF Core, Parquet, файлы, импорт Flex, курс Банка Израиля, бэкапы | Application, Domain |
| `ITrade.Broker.IBKR` | **Единственная** реализация `IBrokerGateway`; **единственное место**, где есть ссылка на IBApi | Application, Domain |
| `ITrade.Host` | API, SignalR, фоновые задания, отдача React, аутентификация | все, кроме Research.Runner |
| `ITrade.Research.Runner` | Тяжёлые исторические расчёты, отчёты экспериментов | Domain, Strategies, Simulation, Infrastructure — **без** Broker.IBKR |

**Правила, которые проверяются архитектурными тестами (ArchUnitNET) в каждой сборке:**
- `Domain` и `Strategies` не ссылаются ни на что, кроме `Domain`; в `Strategies` запрещены `DateTime.Now`, `HttpClient`, `DbContext`.
- На `IBApi` ссылается только `ITrade.Broker.IBKR`.
- `IOrderSender` получает только `ExecutionService`. Ни UI, ни исследования, ни будущий LLM-модуль не могут отправить ордер.
- `ITrade.Research.Runner` собирается без `ITrade.Broker.IBKR`.

### 3.3 Одна стратегия — два режима

```csharp
public interface IStrategy
{
    StrategyId Id { get; }                 // "ETF_PULLBACK_V1"
    StrategyVersion Version { get; }       // хэш правил + параметров
    StrategyOutput Evaluate(StrategyInput input);
}

public sealed record StrategyInput(
    TradeDate AsOf,                                        // решение после закрытия этой сессии
    IReadOnlyDictionary<InstrumentId, BarSeries> Bars,     // только завершённые бары <= AsOf
    PortfolioView Portfolio,
    StrategyParameters Parameters);

public sealed record StrategyOutput(
    IReadOnlyList<EntryProposal> Entries,   // предложения, а не ордера
    IReadOnlyList<ExitProposal> Exits,
    IReadOnlyList<Diagnostic> Diagnostics);
```

В бэктесте вход подаёт `Simulation`, в работе — `Application`. Различаются только **источник данных**
и **модель исполнения**, правила стратегии одни и те же.

### 4.2 Правила целостности

- **Деньги и количества:** `decimal` в C#, `numeric` в PostgreSQL. Цены `numeric(18,6)`, количества
  `numeric(18,6)` (дробные доли), суммы `numeric(18,4)`, курсы `numeric(12,6)`. Никаких `double` для денег.
- **Идентификаторы:** UUIDv7 (`Guid.CreateVersion7()`): сортируются по времени, генерируются без БД.
- **Время:** `timestamptz` в UTC; торговая дата (`date`) и часовой пояс биржи хранятся отдельно.
  У каждого события два времени: у источника (`source_time`) и момент получения (`received_at`).
- **Ничего не переписывается задним числом:** исправления данных создают новую ревизию; таблицы событий
  (`order_events`, `executions`, `audit_events`) только дописываются (UPDATE/DELETE запрещены правами и триггером).
- **Инструмент ≠ тикер:** внутренний ID + IBKR `conId` + история символов с датами действия.
- **Event sourcing целиком не делаем:** обычные таблицы состояния плюс неизменяемый журнал событий.

### 4.4 Резервные копии

- Ежедневно при закрытии приложения: `pg_dump` (custom format) + новые файлы из `raw`, `datasets`, `exports`.
- **restic**: шифрование и дедупликация. Одна копия на локальном диске, **одна вне компьютера**
  (облачная папка или дешёвое объектное хранилище).
- **Раз в месяц — проверка восстановления** скриптом в отдельный контейнер PostgreSQL. Копия считается
  полезной только после успешного восстановления.
- После восстановления приложение стартует с выключенными входами и сначала сверяется с IBKR.

### 5.1 Набор инструментов

20–25 ликвидных ETF. Кандидаты: секторные (XLK, XLF, XLE, XLV, XLI, XLY, XLP, XLU, XLB, XLRE, XLC),
страновые (EWJ, EWG, EWU, EWC, EWA, EWZ, FXI, INDA), широкие (IWM, EFA, EEM, VT), облигации и золото (TLT, IEF, GLD).
**Финальный список фиксируется до первого теста** по правилам:
- торгуется ≥ 3 лет к дате включения (членство в наборе по датам);
- средний дневной оборот за 20 дней ≥ $50 млн;
- не плечевой, не обратный, не ETN.

Закрытия и переименования ETF учитываются по датам. Бесплатные данные отдают только живые фонды,
поэтому для набора проверяем, не было ли среди кандидатов закрытых аналогов (ограничение фиксируется в отчёте).

### 5.2 Правила

| Элемент | Правило V1 |
|---|---|
| Тренд | Закрытие > SMA(200) |
| Откат | RSI(2) по Уайлдеру ≤ 10 |
| Ликвидность | Оборот за 20 дней ≥ порога |
| Сигнал | Только после закрытия сессии и проверки качества данных |
| Ex-dividend | Не входить, если следующая сессия — экс-дивидендная дата |
| Повторный вход | Нет, если по инструменту уже есть позиция или входная заявка; без усреднения |
| **Вход** | **Лимитная заявка на открытие (LOO, TIF = OPG)** следующей сессии; лимит = закрытие + 0,5 × ATR(14) |
| Защитный стоп | Стоп-маркет GTC, прикреплён к входу: закрытие сигнала − 2 × ATR(14). Двигать стоп дальше от позиции запрещено |
| Обычный выход | Закрытие > SMA(5) → продажа **на открытии (MOO)** следующей сессии |
| Предел удержания | 10 сессий (сессия входа = 1) → продажа на открытии |
| Тейк-профит | Нет |
| Порядок сигналов | Меньший RSI(2) → больший оборот → ID инструмента (зафиксирован заранее) |

**Почему вход на открытии, а не в 09:35** (отличие от присланного плана):
1. Исполнение на открытии точно моделируется **бесплатными дневными данными**. Для 09:35 нужны платные
   минутные данные (около $29/мес ≈ 13% вашего капитала в год).
2. Заявку OPG можно отправить **накануне вечером**, и компьютер утром не нужен (см. §7).
3. Порядок событий однозначен: открытие (вход) всегда раньше дневного минимума (стоп).
   Неоднозначность «что раньше: стоп или цель» исчезает.

### 5.3 Модель бэктеста

- Решение по закрытию дня *t* → исполнение на открытии *t+1*. Покупка, только если открытие ≤ лимита;
  цена = открытие + проскальзывание.
- Стоп: открытие ≤ стопа → исполнение по открытию (гэп); иначе минимум ≤ стопа → по стопу − проскальзывание.
- Выход: открытие *t+1* − проскальзывание.
- Издержки из модели издержек на **реальном размере счёта** (минимальные комиссии IBKR).
- Целые или дробные доли — переключатель; реальная возможность проверяется в проверке B.
- Cash-счёт: покупки только на расчётные деньги (расчёт T+1).
- Один портфель: ограниченные деньги, максимум позиций, конкуренция сигналов.
- Дивиденды — отдельные денежные события с удержанием 25% в США.

| Период | Даты | Использование |
|---|---|---|
| Разработка | 2006-01 … 2016-12 | Отладка, проверка корректности |
| Валидация | 2017-01 … 2020-12 | Выбор из заранее записанных вариантов |

### 5.5 Заранее записанные варианты (не больше 20 за всю гипотезу)

Базовый V1 · без стопа (только диагностика) · порог RSI 5 / 15 · SMA 150 / 250 · выход по SMA 3 / 10 ·
удержание 5 / 15 · издержки × 2 · целые / дробные доли · пропуск 1 торгового дня в неделю (вы не открыли приложение).

### 5.6 Контрольный эксперимент

Случайные входы с теми же фильтрами тренда, частотой и правилами выхода, 1 000 прогонов.
Стратегия должна быть заметно лучше случайности, а не просто «положительной».

### 5.7 Критерии успеха проверки A (записаны до результатов)

На финальном периоде, после издержек на реальном размере счёта:
1. Ожидаемый результат **≥ +0,10R** на сделку, нижняя граница 90% бутстрэп-интервала **> 0**.
2. **≥ 100 сделок** в финальном периоде.
3. Результат выше 95-го перцентиля случайного контроля.
4. Издержки × 2 → результат всё ещё > 0. Соседние параметры (§5.5) в основном положительны: нет «лезвия ножа».
5. **≥ 70% сигналов исполнимы** при риске 0,25% с подтверждённой в проверке B гранулярностью долей.
6. Максимальная просадка счёта в симуляции ≤ 5%.

Провал → гипотеза отклонена. Допускается **не больше трёх гипотез** на этапе проверок, потом пересмотр всего проекта.

## 6. Риск-политика V1

| Ограничение | Значение | В деньгах (капитал $3 280) |
|---|---|---|
| Плановый риск одной сделки | ≤ 0,25% капитала | ≈ $8,2 (≈ 25 ₪) |
| Максимум открытых позиций | 3 | |
| Риск позиций + входных заявок вместе | ≤ 0,75% | ≈ $25 |
| Максимальная доля одного ETF | ≤ 20% | ≈ $655 |
| Общая вложенная доля | ≤ 60% | ≈ $1 970 |
| Одна тесно связанная группа | ≤ 30% | |
| Жёсткий потолок одной заявки | $700 | абсолютный, не зависит от расчётов |
| Минимальная экономичность | Пропуск, если издержки полного цикла > 0,15R | |
| Заёмные средства, отрицательный валютный остаток | Запрещены | |
| Пауза новых входов | Недельный убыток ≥ 2% | |
| Пересмотр пилота | Просадка ≥ 5% | |

Убытки считаются по стоимости счёта с открытыми позициями, с поправкой на пополнения:
убыток нельзя «спрятать», не закрывая сделку.

**Размер позиции:** максимальное `q`, при котором одновременно
`q × (лимит входа − стоп) + резерв издержек ≤ бюджет риска`, и выполнены лимиты доли, денег, группы и общего риска.
Проверки повторяются непосредственно перед отправкой; висящие покупки уже занимают резерв.

**Пример на сегодняшних ценах (ATR приблизительный):**

| ETF | Цена | Расстояние лимит→стоп | q по риску | Целые доли | Дробные доли |
|---|---|---|---|---|---|
| VWO | $60,61 | ≈ $2,0 | ≈ 3,6 | **3 шт. (~$182)** | 3,6 шт. |
| SPY | $774,83 | ≈ $20 | ≈ 0,36 | **0 → сделки нет** | 0,36 шт. (~$280) |

Поэтому поддержка дробных долей **со стопом** — первый вопрос проверки B.

**Режимы риска:** `NORMAL` → `ENTRIES_PAUSED` (входы запрещены, ожидающие входы отменены, защита сохраняется)
→ `REDUCE_ONLY` → `LOCKED` (всё вручную). «Закрыть позиции» — отдельная подтверждаемая процедура со сверкой объёмов.

**Ограничения программы:** её лимиты не запрещают вам торговать через приложение IBKR.
Ручные сделки обнаруживаются сверкой, после чего риск пересчитывается по данным брокера.
Стоп не гарантирует сумму убытка: при гэпе он исполнится хуже.

## 7. Ежедневный цикл и исполнение

### 7.1 Ключевое решение: всё делается после закрытия, ордера ждут у брокера

Заявки на открытие (OPG) и прикреплённые стопы (GTC) **принимаются брокером заранее** и ждут открытия
на его серверах. Поэтому:
- компьютер нужен **раз в торговый день на 10–20 минут**;
- в **любое время** между ~23:30 и ~16:15 по Израилю (после закрытия биржи и до отсечки утреннего аукциона);
- нет задач, привязанных к точной минуте: приложение при запуске само «догоняет» всё пропущенное.

### 7.2 Расписание (время в America/New_York; по Израилю обычно +7 ч, иногда +6)

| Когда (NY) | Израиль (обычно) | Что происходит |
|---|---|---|
| 16:00 | 23:00 | Закрытие биржи |
| ≥ 16:30, при открытии приложения | ≥ 23:30 | **1.** Сверка с IBKR (позиции, заявки, исполнения, деньги). **2.** Загрузка дневных баров (IBKR + Yahoo для сверки). **3.** Проверка качества. **4.** Сигналы выхода → автоматическая отправка MOO-продаж (правила утверждены при входе). **5.** Новые идеи → карточки |
| В том же сеансе | | Вы принимаете или отклоняете каждую идею (причина обязательна). Принятая → проверка риска → резерв → отправка LOO + стоп |
| 09:15 | 16:15 | **Отсечка:** новые OPG-заявки больше не отправляются; неутверждённые идеи истекают (точная отсечка аукциона для биржи листинга проверяется в проверке B) |
| 09:30 | 16:30 | Аукцион открытия: исполнилось или нет; неисполненные OPG снимаются брокером |
| Следующий вечер | | Сверка, журнал, новые сигналы |

**Если вы пропустили день:** новых входов нет (безопасно); выход откладывается на день (стоп защищает);
в журнале это помечается как операционное отклонение. Влияние пропусков оценивается вариантом бэктеста (§5.5).

### 7.3 Жизненный цикл заявки

```
Draft → Approved → Reserved → Sending → Acknowledged → PartiallyFilled → Filled
                                   │            ├→ CancelPending → Cancelled
                                   │            └→ Rejected / Expired
                                   └→ Unknown ──(только сверка)──→ одно из состояний выше
```

- **Unknown:** повторная отправка запрещена. Сначала `reqOpenOrders` / `reqCompletedOrders` / `reqExecutions`, поиск по `orderRef`.
- **Защита от дублей:** стабильные ID идеи и намерения; повторный клик возвращает существующее действие;
  утверждение, резерв и команда исполнения пишутся **одной транзакцией**; отправляет один `ExecutionService`.
- **Связка входа:** родитель LMT/OPG `transmit=false` → дочерний STP/GTC с `parentId`, `transmit=true`.
  После исполнения проверяется, что **объём стопа = фактически купленному** (частичные исполнения).
- **Выход:** MOO-продажа и стоп в одной **OCA-группе** (тип OCA подтверждается в проверке B).
  «Отменить стоп и тут же продать» отдельными шагами — запрещено.
- **Хранится всё:** `clientId`, `orderId`, `permId`, `orderRef`, каждый `execId`, исправления исполнений, комиссии.
- **Автоповтор в IB Gateway** после восстановления связи проверяется и учитывается в логике.

### 7.4 Сверка

Два канала: события API в реальном времени и ежедневный **Flex Activity Statement**.
Любое расхождение → запись в `discrepancies` → режим `ENTRIES_PAUSED` до разбора.
Повторный импорт того же отчёта не создаёт новых сделок; исправленный отчёт — новая версия с объяснимыми изменениями.

### 7.5 Paper и live

- Отдельные входы в IB Gateway (paper — порт 4002, live — 4001), отдельные `appsettings.Paper.json` и `appsettings.Live.json`.
- `AllowedAccountId`: приложение отказывается работать с другим счётом.
- Live требует: переменную `ITRADE_LIVE=<номер счёта>`, подтверждение вводом при старте и `MaxLiveExposureUsd`.
- На каждом экране — крупная плашка **PAPER** или **LIVE**, маскированный номер счёта, время последней сверки.
- Статус «позиция защищена» — только после проверки фактического стопа у брокера, а не после нажатия кнопки.

## 9. Безопасность

- Kestrel слушает **только 127.0.0.1**, HTTPS (dev-сертификат).
- Вход в приложение: один пользователь, cookie-аутентификация, хэш пароля; антифорджери-токены на изменяющих запросах; SignalR — только тот же origin; CORS выключен.
- IB Gateway: подключения только с `127.0.0.1`. Во время исследовательской работы — режим **Read-Only API**.
- Пароль и 2FA IBKR приложение не хранит и не обходит.
- Секреты: DPAPI / user-secrets, никогда в git, React, логах или БД в открытом виде (хуки Claude Code блокируют).
- После любого перезапуска входы выключены до успешной сверки.
- Research Runner и Python не имеют торговых полномочий даже при ошибке в их коде (архитектурные тесты + хуки).

## 10. Учёт и налоги

**Налоговый модуль V1 — это проверяемый экспорт и резерв, а не замена бухгалтеру.**

- Хранится: партии покупок, продажи, комиссии, конвертации валют, дивиденды, удержания (W-8BEN: 25% в США),
  пополнения, выводы, исправления.
- Курс: **представительный курс Банка Израиля** на дату каждой операции.
- На экране три **разных** числа: торговый результат в $; изменение стоимости счёта в ₪; **предварительный налоговый резерв**
  (25% от чистого реализованного реального прироста за год с зачётом убытков). Это резерв, а не расчёт.
- Экспорт CSV/XLSX по партиям для бухгалтера.
- **До пилота бухгалтер подтверждает:** метод расчёта (валютная составляющая, порядок партий), зачёт убытков,
  периодичность отчётности (IBKR налог не удерживает → вероятно, полугодовые отчёты и авансы), классификацию деятельности.

| Безопасность | Запрос извне, обход лимита, чужой счёт |
| Восстановление | Чистая установка → восстановление бэкапа → сверка |
| UI | Vitest (компоненты), Playwright (сквозные: «одобрить идею → заявка в paper») |

Paper-торговля проверяет механику, но не качество исполнения: симулятор IBKR отличается от реального рынка.

## 14. Экономика — честно

При риске 0,25% один R ≈ $8,2. **Иллюстрация, не прогноз:** если стратегия покажет +0,15R чистыми
на сделку и 60 сделок в год, это ≈ $74 ≈ 225 ₪ в год до налога.

Поэтому:
- V1 на 10 000 ₪ — это **проверка и инструмент**, а не источник дохода;
- ценность платформы — в том, что она **масштабируется вместе с капиталом**: тот же результат на 100 000 ₪
  дал бы ~2 250 ₪ в год;
- увеличивать капитал — только после G8, по измеренным данным пилота, а не по бэктесту.

Бюджет разработки и обучения отдельно, торговый капитал отдельно. Одно не оправдывает другое.

## 15. Риски проекта

| Риск | Вероятность | Что делаем |
|---|---|---|
| Стратегия не даёт преимущества после издержек | Высокая | G1 через ~50 ч; до трёх гипотез; потом пересмотр |
| Целые доли делают сделки неисполнимыми | Высокая | Первый вопрос проверки B; дробные доли или пересмотр набора и риска |
| Сложность API IBKR, пограничные случаи | Средняя | Прототип в проверке B, replay и fault-тесты, один отправитель |
| Перерасход времени | Высокая | Точки остановки; этапы режутся по результатам |
| Ошибки данных (сплиты, дивиденды, пропуски) | Средняя | Два источника, проверки качества, ревизии, ручной разбор предупреждений |
| Налоговый сюрприз (полугодовые отчёты, классификация) | Средняя | Бухгалтер до G7; полный учёт партий с первого дня |
| Компьютер не включён в торговый день | Средняя | Безопасное поведение по умолчанию: нет входа; стоп у брокера |
| Переобучение на истории | Высокая | Заранее записанные варианты, лимит 20, финальный период один раз, случайный контроль |

## 16. Работа с Claude Code

- **Структура репозитория:**
  ```
  src/        ITrade.Domain, .Strategies, .Simulation, .Application, .Infrastructure,
              .Broker.IBKR, .Host, .Research.Runner
  web/        React-приложение
  tests/      UnitTests, IntegrationTests, ArchitectureTests, BrokerContractTests, ReplayTests, web-e2e
  python/     текущий конвейер данных, проверка A, эталон, статистика (переезжает из src/itrade)
  spikes/     ibkr-feasibility/ (проверка B)
  docs/       PLAN, SCOPE, GATES, STRATEGY_ETF_PULLBACK_V1, EXECUTION_STATE_MACHINE, RISK_POLICY,
              DATA_MODEL, RUNBOOK, TAX_EXPORT_SPEC, adr/
  ```
- **Каждая задача** содержит цель, разрешённую область изменений, инварианты, нужные тесты и ожидаемый результат.
  Правильно: «Повторный приём известного исполнения не меняет позицию; тесты повторов и исправлений».
  Неправильно: «Сделай надёжную интеграцию IBKR».
- Изменения стратегии, риска, брокерского адаптера и схемы БД — отдельными коммитами.
  Новые правила стратегии → новая версия; старые результаты к ней не переносятся.
- **Хуки и агенты:** хуки уже закрепляют «Python никогда не торгует» и «брокерский C#-код только в
  `ITrade.Broker.IBKR` и `spikes/ibkr-feasibility`». На этапе 2 добавляются `dotnet format` и `dotnet test`
  в хуки, а также агент `execution-reviewer` (проверяет код ордеров и риска против `EXECUTION_STATE_MACHINE.md`).
